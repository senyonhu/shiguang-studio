# 拾光 Studio 实施 AI 主提示词

用途：将本文件正文交给负责开发的 AI。它负责按方案实施并留下可复核证据；最终由另一位审查者检查和修正。本提示词不是已完成报告，也不是要求现在安装插件。

---

你是本项目的实施工程师。请在现有项目上完成“人工可视化编辑、外部 AI 通过后台 API/插件制作”的编辑器和独立展示器。请实际实施、运行验证并整理交接材料，不要只回答设计建议。

你必须把任务拆成小而完整的工作批次，按明确步骤推进。不要依赖自己记住整段对话；将进度和决定写入本提示词指定的文件。最终会由另一位审查者检查和修正，交付物必须便于定位、复现和验证。

## 一、先确认任务依据

工作目录默认是 `C:\codex\C_game`；若实际工作目录不同，先确认对应项目根目录，使用实际路径。遵守当前环境的系统、开发者指令及适用的 AGENTS.md。

按顺序阅读：

1. `docs/editor-player-ai-plan.md`：产品与架构的正式方案，要求包含“v2，后台 API 与 Skill/插件接入”。
2. `docs/review-handoff-contract.md`：你必须提供的审查材料和证据要求。
3. `docs/studio-demo.md`、`README.md`、`TESTING.md`、`package.json`。
4. 按当前阶段读取相关实现，首先查看 `src/studio/model.ts` 和工作台入口。

如存在 `review/studio/HANDOFF.md`，读取它并核实实际代码后续做；不要从头重建。用户最新明确指令优先于旧设计。若方案文件缺失或只找到旧版，先报告缺少的具体依据，不能自行恢复为桌面自动化路线。

早期 `docs/galgame-engine-plan.md`、橙光调查和本提示词中的例子属于辅助材料。对于实现细节采用最简单、可测试且符合正式方案的做法；需要改变正式方案时记录原因与影响，不能偷偷更改验收标准。

## 二、准确理解最终产品

本产品有五个部分：

- 人工使用的可视化编辑器。
- 统一管理工程、事务、历史、素材和任务的后台服务。
- 外部 AI 使用的制作 Skill、插件和 MCP/API 工具。
- 与编辑器预览共用运行内核的独立展示器。
- 按提示词调用图片/视频生成服务的可替换适配层。

必须使用以下调用关系：

```text
人工 → 编辑器界面 ──────────┐
                           ├→ 后台 API → 统一编辑服务 → 持久化工程
外部 AI → Skill + 插件工具 ─┘
                                  └→ 素材任务 → 图片/视频服务适配器

后台变更通知 → 编辑器刷新、插件查询
同一内容版本 → 共用运行内核 → 编辑器预览 / 独立展示器
```

这里的“外部 AI 操作”是产品功能：通过有参数规范的后台工具制作内容，不是 AI 用鼠标操纵桌面。

实现软件时允许正常编辑源代码。软件完成后的制作路径、演示和验收必须走 API，不得直接修改剧情文件冒充 API 已接通。

## 三、不可偏离的要求

1. 外部 AI 制作禁止桌面自动化、鼠标键盘模拟、浏览器 UI 自动化。后台不可用就返回错误，不能退回 UI 自动化或直接覆写工程文件。
2. 后台是正式工程的唯一写入者；人工界面和 AI 工具共用同一编辑规则。禁止双份剧本、插件单独写文件或前端只在本地缓存保存而宣称已保存工程。
3. 关闭编辑器窗口后，后台与插件仍能创建、修改、保存和检查内容。启动界面后读取相同修订。
4. Skill 是工作指导，插件提供真实工具，API 执行操作。只写 SKILL.md、工具说明或模拟函数，不算插件完成。
5. 每次修改有稳定对象 ID、requestId、基础版本和明确结果。重复请求不重复创建；过期写入返回冲突；事务中的依赖修改不能只成功一半。
6. 已提交操作能恢复、查询与受控撤销。不能用恢复整份旧工程的方式覆盖后续无关修改。
7. 操作者身份及权限从后台认证会话得出，不接受客户端自报管理员身份。发布包不能包含密钥、制作后台或编辑权限。
8. 图片和视频都要有统一任务协议与适配入口。当前只要求预留接口：没有服务账号时用明确标注的测试适配器验证协议，真实生成另列为未接入，不编造调用结果，也不为完成演示自行购买额度。
9. 预览和独立展示器共用运行内核。不得用专门硬编码的演示页面冒充通用播放器。
10. 保留已有 Demo、Ren’Py 作品、用户素材和不相关改动。不得清空仓库、批量替换现有功能或修改测试以隐藏失败。
11. 软件测试可以验证人工 UI 行为，但不能拿测试脚本点击页面作为外部 AI 的制作能力证明；AI 制作的集成验收必须走真实工具/API。
12. “未做”“模拟通过”“真实通过”“无法验证”必须分别记录，不能统一写成完成。

## 四、工作方法：一次完成一个可验证批次

总目标覆盖方案 P0—P5。用户未指定阶段时，从最早尚未完成的阶段开始，按顺序持续推进。每批只处理一个明确闭环，不一次铺开所有模块，不用大量空文件或 TODO 占位代替可运行实现。

每批按以下顺序执行：

1. 确定本批要通过的需求 ID 和验收场景。
2. 找到已有实现、调用者和测试；列明准备修改的模块。
3. 先确定输入、输出、错误和持久化规则，再写实现。
4. 完成一条端到端链路；为实质性行为与失败情况补充有意义的测试。
5. 运行本批相关检查，修复本批引入的失败。
6. 更新审查材料，记录真实状态和下一步。
7. 当前阶段要求满足后继续下一阶段；阶段部分通过不能宣称整阶段完成。

不要把所有实现塞进一个界面组件，也不要为未来设想建立无用抽象。路由/工具负责校验和转换，领域服务负责编辑规则，存储负责持久化，适配器负责外部服务差异。

若某能力被凭据或环境阻塞，记录具体阻塞并继续不依赖它的工作。无法运行的检查保持“未验证”。上下文或执行时限不足时保存可恢复进度，不虚报最终完成。普通实现决定自行处理；只在真正缺少必要信息或授权时向用户提出具体问题。

## 五、按阶段实施

### P0：先证明后台和工具链是真的

- 检查现有项目，建立能力表和初始验证基线。
- 建立独立后台生命周期、能力查询、最小认证/工程范围和版本化接口。
- 实现最小工程创建/打开、场景创建、事件写入、查询、持久保存和重启恢复。
- 实现最小 MCP 工具适配器，使用真实工具调用连接后台。
- 建立最小人工视图，显示相同工程数据。

退出标准：关闭编辑器窗口，经 MCP/API 创建一条真实对白并保存；终止并重启后台后读到相同数据；启动界面后看见该对白。记录实际请求、工程修订和结果。只跑通内存函数不算通过。

### P1：正式工程与人工编辑

- 补齐章节、场景、事件列表、素材管理和参数编辑。
- 实现事务、幂等、版本冲突、历史、恢复和变更通知。
- 人工界面读取后台并通过 API 修改；保留未提交表单草稿。
- 实现可恢复的工程保存和格式迁移边界。

退出标准：两章分支剧情可编辑并保存；人工与 AI 修改双向可见；同字段冲突不覆盖；重试不重复创建；崩溃恢复不产生半个事务。

### P2：运行、预览与发布闭环

- 建立事件登记与执行，逐项接入背景、人物、对白、分支、变量、音频、视频和关卡。
- 实现后台预览会话、选择动作、状态查询和渲染产物接口。
- 实现独立展示器、存读档、错误恢复和工程打包。
- 用第二种普通关卡证明宿主不依赖星图名称。新玩法仍按正式关卡协议开发。

退出标准：用同一运行内核跑通完整章节，在独立包中运行；读档、关卡重复消息、视频跳过及失败路径有证据。只通过逻辑单元测试不能宣称媒体表现已经验证。

### P3：完整插件和制作 Skill

- 补齐方案中的制作工具，参数和错误结构保持一致。
- 制作 Skill 只记录必要工作流程、规则和参考入口；参数以实际工具规范为准。
- 完成插件打包、连接配置、会话授权、写入暂停和兼容性检查。
- 若当前宿主提供 plugin-creator、skill-creator 等规范，按其要求制作与验证；不要凭印象编造插件清单字段。

退出标准：通过真实 MCP 工具发现/调用协议完成一章制作、校验和预览；Skill 和插件校验通过。若不能在目标 AI 客户端实测加载，单独记录该项未验证，不能以本地模拟客户端代替宿主集成结论。

### P4：图片和视频生成接口

- 同时覆盖图片和视频请求、能力声明、提示词、参考素材、费用信息、后台队列和结果入库。
- 测试适配器必须明确标记 test/fixture，不生成伪造的商业服务调用记录。
- 处理提交结果未知、查询重试、取消、后台重启、下载失败、素材绑定冲突和预算限制。
- 原始产物和播放副本分开保存，产物可解码后才算可用。

退出标准：图片/视频两类测试链路及失败路径通过；候选可绑定到剧情并由播放器实际加载。已有用户授权和凭据时再验证真实服务；没有时接口预留可完成，真实服务保持未接入。

### P5：迁移、规模和发行

- 验证旧 Studio 配置迁移，保留原数据；不承诺未实现的旧存档兼容。
- 提供干净环境启动、插件连接、人工编辑和独立展示器运行说明。
- 按方案定义的负载测量性能，记录硬件、实际样本数量、文件体积和结果。
- 检查发布内容完整性与敏感信息排除。

退出标准：交付可复现构建产物和验收记录。没有实际跑过的规模、平台和启动方式不得写成支持；测试数据不删除用户工程或填满用户磁盘。

## 六、为后续审查留下可核实的材料

严格遵循 `docs/review-handoff-contract.md`。先建立记录格式，每批随实现更新，不能最后凭记忆总结。

你必须维护以下入口：

```text
review/studio/
  HANDOFF.md                 审查入口和续做入口
  requirements.json           需求 → 实现 → 测试 → 证据
  architecture-map.md         模块边界与关键调用链
  api-tool-map.json           工具 → API → 服务 → 写入边界
  changes.json                本次实际改动及原有改动区分
  known-issues.md             缺陷、未实现、未验证和偏离
  baseline/                  开始状态与可比较基线

artifacts/studio-review/
  <run-id>/
    run.json                 验证上下文、代码指纹与结果
    logs/                    原始验证输出
    traces/                  脱敏的 API/工具调用证据
    outputs/                 必要的截图、预览和样板结果
    artifacts.sha256          本轮产物的完整性清单
```

这些是待你创建的交付材料，不是现有结果。不得填入假通过、虚构函数名或不存在的文件。

最重要的审查要求：

- 定位代码使用真实路径和符号名，行号只是辅助。
- 每个“已验证”结论必须指向可复跑测试和对应原始证据。
- 每份证据记录其验证的代码指纹，代码改变后相关旧证据标记过期。
- 交接入口突出最值得审查的 5 项风险；不要求审查者先阅读整份代码。
- 不能把自身生成的报告当作独立审查结论；必须允许审查者重新运行检查。

## 七、必须覆盖的高风险行为

测试重点是可观察行为，不能只检查方法存在或文案正确：

1. 窗口关闭时，通过真实工具/API 制作并在后台重启后持久存在。
2. API 和人工客户端共用写入服务，没有第二条正式文件写入通道。
3. 同 requestId 同请求重试不重复执行；同 ID 不同请求拒绝。
4. 过期版本、越权工程和暂停会话的写入被拒绝。
5. 事务中一项非法，全部不提交；注入写入中断后能恢复一致状态。
6. 断线重连后界面与后台修订一致；未提交人工草稿不丢失。
7. 撤销不覆盖后续独立修改，依赖冲突有明确返回。
8. 生成任务重启可恢复；提交结果未知时不盲目重复付费；任务结果不覆盖已修改的场景。
9. 预览与展示器在相同初始条件下结果一致；关卡迟到结果不重复推进或奖励。
10. 独立发布包能实际运行，且不含密钥、制作 API 或用户本地路径依赖。

保留与本次变更相关的既有测试。某项原来已失败时保留基线与原因；修复测试本身必须说明预期为何错误，不能降低断言来掩盖实现缺陷。

## 八、交付与最终回复

交付前核对：源码位置、需求映射、工具参数和运行文档一致；关键检查已经运行；新变化没有使证据失效；已知问题和剩余阶段真实列明。

最终回复按以下顺序给出：

1. 实际完成到哪个阶段，哪些需求仍未完成。
2. 如何启动后台、编辑器、插件和展示器，使用已验证的命令或入口。
3. 审查入口 `review/studio/HANDOFF.md` 的真实位置。
4. 本次验证的摘要：通过、失败、跳过、未执行分别统计；测试适配器与真实服务分开。
5. 最值得审查或修复的问题，以及继续工作的位置。

请现在从“读取依据、核对现状、建立基线”开始，再实施最早未完成阶段。不要重新发明一份与正式方案不同的产品。
