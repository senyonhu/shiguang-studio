# 《术式纪元》技术验证 Demo：旧塔的最后一盏灯

**Ren’Py 单机离线实施版 v1.1｜2026-09-29**

本稿为完整设计与开发规格，尚未制作可运行游戏。以2026-09-28《旧塔的最后一盏灯_Demo设计方案》为内容基础，形成独立的 Ren’Py 实施版本。剧情、三关点灯任务、未来自我伏笔继续沿用；将原 Vue＋Ink 游戏表现层调整为 Ren’Py，代码编辑改为与入门任务匹配的轻量方案。本次按单机优先要求，将编译、执行与判题全部迁移至学生本机，移除教师侧服务器与联网运行依赖。以下尺寸、参数和工期均是设计建议或验证目标，不是已取得的实测结果。

## 1. 一句话方案与开发目标

制作一款约15—20分钟的 Windows 二维视觉小说：学生从黑暗旧塔醒来，和守塔学徒“璃”修复点灯术式，通过真实的 C 语言编译运行解决三个连续问题，打开塔门，看见异世界，并收到未来自己的警示。

游戏主引擎使用 Ren’Py；C编译器、受限执行环境与本地判题模块随游戏一起分发。学生解压完整游戏文件夹，双击启动程序，在断网状态下完成全部三关和存档。Ren’Py负责游戏，本地模块负责真实C编译、执行和判分；不启动HTTP服务，不需要教师电脑在线。

本次需要回答五个问题：

1. 学生是否愿意为了人物和故事，继续修改代码？
2. 学生是否能看懂“代码输出—灯光变化”的对应关系？
3. Ren’Py 的输入界面是否足以支持当前三关？
4. 真实 C 执行、错误反馈、存档恢复能否稳定连起来？
5. 新增下一章时，能否主要替换剧情和任务数据，而无需重写基础模块？

验收重点是可玩性、技术可行性和问题诊断能力；小样本试玩不用于证明教学效果。

### 1.2 教学定位

零基础学生可在脚手架帮助下体验，但循环属于先行接触。学过变量、输入输出和比较运算的学生可以将其用作循环边界练习。不能用“改对一次”“四组测试全过”推断学生已掌握循环。

本次只强调三个可观察目标：能将输出编号与灯对应；能解释为什么最后一盏没有亮；能说明为什么换一组输入还需要验证。头文件、main、scanf等内容可展开查看，不在20分钟内展开所有语法。

## 2. 世界规则与剧情动机

旧塔曾依靠“术式板”维护照明。术式板读取程序的文本输出，把每一行灯编号转换为一次点灯命令。旧代码损坏，塔门又由整套回路的验证结果控制。璃懂塔的结构，却无法修复这段术式；玩家能读懂代码，但不了解这个世界。双方各有作用。

必须在首次任务明确说明：“C程序输出的是文字；这块术式板按约定把文字变成点灯指令。”不得暗示 printf 在所有 C 程序里都能直接施法。

| 教学对象 | 游戏呈现 | 必须保留的真实含义 |
|---|---|---|
| 源代码 | 术式文本 | 实际提交的 C 程序 |
| 编译 | 解析术式 | 将源代码转换为可执行程序 |
| printf | 发送灯编号 | 向标准输出写文本 |
| n | 当前回路灯数 | 从标准输入读入的整数 |
| i | 当前灯编号 | 随循环更新的变量 |
| 循环条件 | 是否继续点下一盏 | 每轮开始前判断条件 |
| 多用例 | 更换回路规模 | 同一份代码处理不同输入 |
| 超时 | 术式未能停止 | 执行器终止超出资源限制的程序 |

没有答错扣血和倒计时死亡。悬念来自环境、璃的处境和塔外世界；错误反馈支持重新观察、修改和验证。

### 3.1 标题画面

标题《术式纪元》，副标题《旧塔的最后一盏灯》。旧塔背景中仅有很弱的门缝光。按钮为“开始旅程”“继续旅程”“设置”“退出”。加载时检查随包编译器、运行器、任务文件与用户数据目录。失败时明确提示“本地运行组件缺失或无法启动”，提供重试和诊断信息；允许看开场，但进入任务后不得假装编译成功。

### 3.2 黑暗中醒来

黑屏出现滴水声，画面逐渐显露石地和熄灭的灯。玩家输入昵称可选，直接继续使用“旅人”；昵称输入不是游戏启动的阻碍。

- 旁白：“你醒来时，掌心压着冰冷的石板。头顶没有熟悉的天花板，只有一圈已经熄灭的灯。”
- 璃：“听得见吗？先别动，前面是断掉的台阶。”
- 选项A：“这是哪里？”
- 璃：“旧塔的下层。等有了光，我带你找出口。”
- 选项B：“你是谁？”
- 璃：“我叫璃。至于你为什么在这里……我也想知道。”
- 两支汇合，璃：“你手边的术式板还在响应。试着把第一盏灯的编号发给它。”

此时璃只有轮廓；完成第一关后才清晰出现，让一次代码修改带来可感知的剧情收益。

### 3.3 第一束光

玩家运行初始代码，终端收到编号0，灯保持熄灭。提示不是“答错了”，而是“收到了编号0；当前灯的编号是1”。修改后，输出行与灯同步高亮。

- 璃：“亮了。它读懂了你写的东西。”
- 玩家：“我只是改了一个数字。”
- 璃：“在这里，一个数字就能决定我们看见什么。”

灯光照出璃，表情由担忧转为放松。任务1首次通过后显示“继续”，由玩家点击推进，不突然收走代码。

### 3.4 修复回廊

- 璃：“这段旧术式应该依次点亮三盏灯。先运行一次，看看它停在哪里。”

初始程序只回放1、2号灯，3号灯暗着。将“成功运行”和“没有完成目标”同时展示。

- 璃：“不是完全失效。前两盏都亮了，问题出在它什么时候停下来。”

学生修正边界后三灯亮起。

- 璃：“第三盏也亮了。但出口接的是另一条回路。”
- 璃：“先别急着复制。只有一盏灯的时候呢？一盏也没有的时候呢？”

### 3.5 全部回路验证

沿用第二关已通过的代码，不强迫学生重新抄写。界面显示四个待验证回路：0、1、3、6。点击“验证全部回路”，逐项返回真实结果。空回路通过时，文字说明“需要零条指令，实际零条指令”，避免学生以为灯没亮就是失败。

成功后璃说：“现在，这几条回路都能正常工作了。”不使用“任何输入都正确”之类超出证据的表述。

### 3.6 开门与世界展开

先保存通过状态，再播放演出。六灯按顺序亮起，门锁纹路显露，石门移开。

- 璃：“走吧。你总得先看看自己来到了什么地方。”

世界展开采用出口背景三层视差与遮罩，在 Ren’Py 内实现。设计镜头如下：

| 时间 | 演出 |
|---|---|
| 0—5秒 | 门缝扩大，冷色石室被暖色晨光切开 |
| 5—12秒 | 前景门框向两侧离开，模拟走出塔门 |
| 12—22秒 | 山谷、浮岛与远处城市逐层展开；主题音乐进入 |
| 22—30秒 | 镜头停稳，显示标题与短暂留白 |

本版优先完成可跳过的分层演出；将来制作成视频时，只替换演出入口。参考的是“局促到开阔”的情绪节奏，采用原创场景与镜头。视频替换方案应单独测试编码和播放，不将普通MP4必然可播作为前提。

画面短暂干扰，只有文字，不新增立绘。

- 玩家：“……没什么。”

## 4. 三关 C 语言任务规格

### 4.1 第一关：第一束光

任务ID：`tower_light_01`。目标：程序正常结束，输出编号1。

```c
#include <stdio.h>

int main(void) {
    printf("0\n");
    return 0;
}
```

编辑方案：显示完整代码，只开放引号内部的数字位置；输入框初值为`0`。学生将它改为`1`。完整源代码由固定模板和可编辑片段组成，界面能查看最终提交版本，本地判题模块按同一模板重建并校验。

这个单字符输入是本关的教学脚手架，不代表C语言只能输出数字，也不代表系统支持任意完整程序编辑。

通过条件：真实编译成功、退出码正常、完整stdout为`1`或`1\n`。没有输入。改变源码后需重新运行，不能沿用旧的通过结果。

三级提示：

1. 看一看，灯上刻着什么编号？
2. 术式板需要收到数字1。
3. 将 printf 引号中的0改成1，再运行。

知识说明：引号内是输出文字；`\n`表示换行。头文件和主函数折叠为“程序骨架”，可看解释但不要求记忆。

### 4.2 第二关：为什么最后一盏不亮

任务ID：`tower_light_02`。固定测试输入`3\n`，期望输出1、2、3，每行一个编号。

```c
#include <stdio.h>

int main(void) {
    int n;
    scanf("%d", &n);

    for (int i = 1; i < n; i++) {
        printf("%d\n", i);
    }

    return 0;
}
```

可编辑范围：`i < n`这一条件表达式，使用单行输入框。允许学生写出其他正确条件，不按标准源码字符串判分。结构性约束只负责限定编辑区域，实际结果仍由真实C运行判定。

进入本关时先运行一次初始代码，观察结果。编译成功，输出1和2，反馈“期望3条指令，实际2条；缺少3号”。

修复示例：`i <= n`。输入框旁显示四张简短说明卡：n是灯数；i从1开始；条件为真才进入本轮；一轮结束后i增加1。

三级提示：

1. 当轮到3号灯时，i和n分别是多少？
2. 把i=3、n=3代入，`3 < 3`成立吗？
3. 试试`i <= n`，允许编号等于灯数的那一轮执行。

可提供一张静态讲解表，必须标记“初始程序示例推演”，不能当作任意学生代码的逐行跟踪结果。

| i | i < 3 | 是否输出 |
|---:|---|---|
| 1 | 真 | 输出1 |
| 2 | 真 | 输出2 |
| 3 | 假 | 循环结束 |

通过后仅显示“当前输入n=3通过”。本关不证明程序能处理其他输入。

### 4.3 第三关：点亮整座塔

任务ID：`tower_light_03`。继承第二关代码，开放整个for循环片段，头文件、输入和return仍为固定骨架。学生无需继续修改正确代码，主要任务是选择输入、观察并验证同一程序。

轻量多行输入支持查看和修改循环片段；控制在约8—12行。若输入体验无法通过阶段1验收，先修复输入控件再进入完整制作，不能以放弃真实编程掩盖问题。

| 用例 | 标准输入 | 期望stdout | 反馈重点 |
|---|---|---|---|
| 空回路 | `0\n` | 空字符串 | 不应输出任何编号 |
| 单灯回路 | `1\n` | `1\n` | 最小非空情况 |
| 已修复回路 | `3\n` | `1\n2\n3\n` | 已见情况 |
| 出口回路 | `6\n` | `1\n2\n3\n4\n5\n6\n` | 数量增大 |

“试运行”使用当前选中的一个输入；“验证全部回路”对一个不可变源码快照执行四组用例。不能以四次不同代码的试运行结果拼凑通关。代码修改后显示“代码已修改，需重新验证”。

本Demo输入范围限定为整数0—6；四组是选定验证样例，不等于穷尽全部可能输入。通过四组并不构成程序普遍正确的证明。

三级提示：

1. 同一份代码要适应不同灯数，不只适应3盏灯。
2. 看看循环条件是否用了n，输入0时是否会进入循环。
3. 参考从i=1开始、在i<=n时继续的写法，并解释n=0为什么不执行。

理解题：“输入0时，没有灯亮，为什么仍然通过？”

- A. 因为程序自动忽略了这个测试。
- B. 因为没有灯需要点亮，循环第一次判断就不成立。
- C. 因为运行时间足够短。

正确答案B。记录首次回答和是否改选；答错可重选，不锁住结局。教师口头迁移追问可用：“如果有4盏灯，最后一个编号是什么？”不新增第四个必过关卡。

## 5. 输出协议、判分与可视化

### 5.1 判分协议

当前三个任务的stdout约定为：每行一个十进制正整数编号；顺序必须正确；不接受额外提示语。统一CRLF为LF；非空输出允许有或没有一个末尾换行；其余内容不随意trim。n=0必须完全空输出，单独一个换行不是空输出。

编号使用通常十进制写法，例如1，不使用`+1`或`01`。此处是任务输出格式约定，不是说它们不属于合法数字表示。格式不合要求时单独提示，避免把格式错误说成算法错误。

判题使用完整输出，不能只比较亮灯个数、不能忽略顺序、不能去重后判对。学生写出不同代码但满足编辑范围和输出约定，应正常通过。

### 5.2 运行结果与游戏显示

| 状态 | 学生看到的反馈 | 是否允许推进 |
|---|---|---|
| 编译/运行中 | “术式正在运行”，保留代码，禁重复提交 | 否 |
| 编译错误 | “这一行暂时无法编译”，可展开原始报错 | 否 |
| 正常结束但答案错误 | 期望/实际对照、缺少/重复/顺序说明 | 否 |
| 通过 | 对应灯光、明确通过标记、“继续” | 是 |
| 运行时错误 | “程序异常结束”，保留stderr详情 | 否 |
| 超时 | “程序未在限制内结束，请检查循环条件” | 否 |
| 输出超限 | “输出过多”，标注截断 | 否 |
| 本地组件不可用 | “本地运行组件无法启动，代码已保留” | 否 |

不会将所有编译错误都归因于缺分号。能可靠识别的错误才给定向中文提示，其余提供中性说明和原始信息。运行状态由本地判题模块计算，界面不能凭动画完成宣告通过。

### 5.3 点灯表现

接收本次结果后，清空本次预览灯态，再按stdout中的有效编号回放，每条约250—400毫秒。输出列表对应行高亮。重复编号表现为该灯轻闪并记录重复，非法编号只报诊断，不访问越界灯位。

stdout是在程序结束后获得的完整结果；逐盏亮起是结果回放，不是实时逐行调试。若程序异常结束后保留部分stdout，只能标注“部分结果，运行失败”，不播放成功演出。

六灯是独立图层，不能烘焙在背景中。任务预览灯态与剧情已修复的灯态分开，避免输入0的试验把故事进度也清空。

### 6.2 代码输入要求

首版采用 Ren’Py 自定义screen与输入控件，实现片段编辑。它不是Monaco，也不承诺VS Code级体验。

- 任务1：一个数字位置。
- 任务2：一行循环条件。
- 任务3：一个简短多行循环块。
- 支持光标移动、退格、删除、复制粘贴；换行键在界面明确说明。
- C代码按原样保留，尤其是花括号、方括号、百分号、反斜杠和引号。
- Ren’Py输入控件的默认排除字符须显式调整；显示源码与编译信息时处理文本标签和插值转义，不能让C代码被当作界面格式。
- 编辑器获得焦点时，空格、回车和字母按键不得触发剧情快进、隐藏界面或切换菜单；运行中禁止编辑或取消后再修改。
- 语法高亮、自动补全、多文件工程、断点调试不属于首版验收。固定骨架可着色，不能用着色暗示已有完整语法分析。

### 6.3 辅助体验

所有状态有文字与图标，不只依赖红绿；静音可完成所有任务；动画可跳过；快速读剧情不能跳过任务；错误不清空代码。提示按需逐级展示，使用提示不扣分，也不形成羞辱性评级。

## 8. 单机技术架构与分发方式

### 8.1 固定采用的离线路线

采用“Ren’Py＋随包WASI SDK编译器＋Wasmtime运行器＋本地判题模块”。学生写的仍然是真实C代码，由Clang编译为WebAssembly模块，再在本机受限环境内执行。WebAssembly在这里是一种程序产物格式，不需要浏览器或网络。

这是一条待阶段1验证的实施路线：须在Windows x64目标电脑验证工具链、printf/scanf、超时、打包和性能后锁定版本。不能把技术选型当作已有成品，也不能在验证失败时静默改成伪判题。

| 模块 | 采用方案 | 职责 |
|---|---|---|
| 游戏引擎 | Ren’Py 8，验证后锁定版本 | 对话、分支、screen、图层、音效、存档 |
| 剧情逻辑 | .rpy脚本与Python | 场景流转、任务入口、状态判断 |
| 代码输入 | 自定义screen＋输入控件 | 单行/多行片段编辑与源码预览 |
| 本地判题 | 随游戏打包的Python模块 | 模板拼装、用例调度、结果比较与记录 |
| C编译 | WASI SDK中的Windows x64 Clang及配套sysroot、链接器 | 按C11生成wasm32-wasip1程序，保留真实编译诊断 |
| C执行 | Windows x64 Wasmtime独立进程 | 执行.wasm文件，接收stdin、返回stdout/stderr |
| 进程管理 | Windows Job Object＋超时与输出监控 | 管理本次编译/运行进程树、取消与退出清理 |
| 保存 | Ren’Py存档＋JSON/JSONL | 剧情、代码草稿、完成收据、体验记录 |

本版移除FastAPI、Judge0、HTTP接口、端口配置、教师侧服务器、Linux执行环境和服务侧数据库依赖。任务与判题逻辑保持模块化，方便将来扩展，但本轮只做一个单机模式。

学生电脑无需另外安装Python、Ren’Py SDK、C编译器、Docker或WSL，也无需修改PATH。开发者预先准备好所需组件并打包，所有运行路径由游戏安装位置定位。目标为普通用户权限启动；学校设备若有应用白名单限制，应遵循既有管理要求，不能要求学生关闭防护软件。

### 8.2 玩家操作与游戏内部过程

玩家操作只有：解压完整文件夹、双击游戏、进入任务、编辑代码、点击运行。内部按以下顺序执行：

1. 本地模块按任务模板拼装源代码，核对任务版本与编辑范围。
2. 为本次提交建立唯一临时目录，保存不可变的main.c快照。
3. 调用随包Clang，将代码编译成program.wasm；编译失败直接返回诊断。
4. 每个测试用例启动一个新的Wasmtime进程，只传入本用例stdin，写完后关闭输入管道。
5. 有界采集stdout/stderr，监控时间与资源；运行结束后比较完整输出。
6. 生成统一结果对象，返回界面，按输出回放灯光。
7. 保存必要收据和日志，清理临时程序与进程。

“验证全部回路”只编译一次源码快照，以同一个.wasm产物依次执行0、1、3、6四个输入。每个用例重新实例化，避免上一组变量或内存状态影响下一组。

### 8.3 本地模块接口

这些是程序内部接口，不是网络API，不监听localhost端口。

| 接口 | 用途 | 关键要求 |
|---|---|---|
| check_runtime() | 检查工具、版本与可写目录 | 可离线完成；返回可读故障原因 |
| load_task(task_id) | 读取本地任务配置 | 核对task_revision、模板版本和编辑区域 |
| start_submission(request) | 启动本次编译判题 | 立即返回submission_id，不堵塞画面 |
| poll_submission(submission_id) | 读取内存中的进度或结果 | 不重复编译，不重复推进剧情 |
| cancel_submission(submission_id) | 终止本次进程树并清理 | 完成终止后再允许下一次运行 |

请求包含run_id、client_request_id、task_id、task_revision、mode、editable_fragment、source_hash和trial_input（仅试运行）。本地模块从固定模板重建源码，重新计算hash。调用方不能指定任意编译器路径、shell命令、资源限制或预期答案。

最终结果包含submission_id、task_id、task_revision、source_hash、status、passed、cases、compile_output、error_kind；每个case包括输入、stdout、stderr、退出状态、耗时和比较结果。同一请求ID重复触发时复用本轮任务，ID相同但内容不同则报告冲突。

所有题目、用例和答案随包存储。单机文件与记录可被用户修改，因此本Demo作为学习与技术验证工具，不将本地结果宣称为防作弊考试成绩。

### 8.4 Ren’Py与本地进程协作

任务screen只收集输入和返回动作意图，由控制器启动后台判题工作。后台线程负责进程等待与管道采集，通过线程安全队列传回普通数据；Ren’Py主线程在交互更新时读取结果并更新游戏变量。后台线程不能直接操作剧情、存档、screen或立绘。

线程、队列和进程句柄放在不参与存档的运行期模块中。不要在screen预测、渲染或Text求值时启动编译器或写文件。任务运行时保持画面与音乐响应，避免在主线程调用长时间阻塞的进程等待。

只允许一个活动提交。取消、返回标题、读档或退出时取消活动任务并回收进程树；游戏异常关闭时，用Job Object的退出清理机制避免遗留编译器或运行器。创建子进程后应在允许其执行前纳入Job，避免先运行后绑定的竞争窗口。

进程使用参数数组和固定工具绝对路径启动，不使用shell拼接执行学生文本；隐藏控制台窗口，stdin/stdout/stderr通过管道传递。连续排空两个输出管道，达到上限立即中止，避免管道堵塞或无限输出占用内存。

### 8.5 执行边界与资源限制

固定C11和wasm32-wasip1目标。保留原三关printf、scanf、变量、比较和for循环。WASI不是完整Windows编程环境；Win32 API、任意DLL、图形库、系统命令、多线程和文件系统编程不属于本Demo支持范围，后续章节涉及这些能力时需单独评估。

学生程序运行时只接入受控标准输入输出，不预开放主机目录，不传入宿主环境变量或网络能力，不加载学生自带原生插件。Wasmtime运行隔离与Job Object职责不同：前者限制来宾程序访问能力，后者限制资源并管理进程结束；Job Object本身不是文件和网络沙箱。

编译器是本机程序，Wasm运行隔离不覆盖编译阶段。固定可信模板、头文件目录和编译选项，片段不允许新增预处理指令、外部头文件、内联汇编或路径引用；检查需考虑续行与等价记号，不能只靠查找几个危险单词。本版面向限定片段练习，不将该限制宣称为可承受任意恶意完整C源码的通用编译沙箱。

| 项目 | 初始设计值 | 实施说明 |
|---|---|---|
| 编译墙钟时间 | 15秒 | 超时结束编译进程树，归类为编译阶段限制 |
| 每用例运行墙钟时间 | 3秒 | 覆盖运行器启动与执行；目标设备实测校准 |
| 来宾线性内存 | 64MiB | 配置运行器限制；不等于整个宿主进程内存 |
| 执行指令预算 | 有限fuel预算，阶段1校准 | 与墙钟超时并用，不把fuel换算为精确秒数 |
| stdout＋stderr采集 | 每用例合计16KiB | 采集时限制，超限终止，不能截断后判成功 |
| 编译诊断采集 | 64KiB | 超限标注，限制后台缓存增长 |
| 完整源码/片段 | 16KiB / 4KiB | 提交前检查 |
| 编译进程树内存 | 暂定512MiB | 与运行器预算分开，根据工具实际需求校准 |
| 运行器进程内存 | 暂定512MiB | 注意JIT和运行器开销，不能套用64MiB来宾限额 |

Wasmtime限制参数须依据选定版本的帮助与文档配置，并验证确实生效；Job Object的内存/终止限制同样需实测。资源限制错误与组件损坏、编译错误、答案错误分开显示。不要承诺零漏洞或任意代码绝对安全。

### 8.6 离线分发与数据位置

交付一个Windows x64 ZIP包，包含启动exe、Ren’Py运行文件、游戏素材、任务数据、toolchain、runtime、许可证和使用说明。保留文件夹结构，解压后双击；单独拷贝一个exe不构成完整分发。首版优先验证完整可用的工具链，再在不破坏依赖的前提下裁剪体积。

Clang、链接器、必要DLL、C头文件、WASI库和Wasmtime必须随包齐备；首次运行不得下载组件。可执行工具放在普通文件目录，不只封装进Ren’Py资源归档。兼容中文用户名、中文/空格路径和移动游戏文件夹；如果工具对路径存在限制，须在打包前解决或给出实测边界。

存档使用Ren’Py保存目录；草稿、提交收据和日志写入用户可写数据目录，临时编译产物写入用户临时目录。不要向可能只读的游戏目录写入。保存目录标识固定，移动游戏文件夹后仍能找到原进度。

更新通过替换完整游戏包完成，保留用户数据，按内容版本检查存档兼容性。无需后台常驻服务、管理员安装、端口开放、联网激活或账号登录。安装包实际大小、解压空间和最低配置在首次打包后记录，不预先承诺“小体积”。

## 9. 游戏状态、存档和学习记录

### 9.1 三种数据分开管理

| 数据 | 保存位置 | 读档规则 |
|---|---|---|
| 故事与本轮任务状态 | Ren’Py存档中的default变量 | 随选定存档恢复 |
| 最近代码草稿 | 本地JSON备份，按run_id与task_id索引 | 读旧档时提示是否恢复较新草稿 |
| 学习事件记录 | 追加式JSONL/导出JSON | 不被剧情回滚删除，按唯一event_id去重 |

核心剧情状态包括schema_version、content_version、run_id、chapter_id、current_task_id、code_drafts、code_revisions、completed_tasks、completion_receipts、current_checkpoint、settings。子进程句柄、管道、线程、队列与future不放进可保存变量，只保存可序列化的ID、字符串和结果摘要。

学习事件包括task_enter、run_requested、run_finished、hint_opened、task_completed、comprehension_answer、save_loaded。使用昵称或随机体验编号即可。代码用于分析修改过程，但不要求收集学生真实身份。

### 9.2 存档节点与实际规则

自动存档：开场结束、每关进入、每关完成、开门前、结算前。任务内提供“保存进度”；提交按钮先将输入框内容写回草稿再运行。

Ren’Py的存档恢复涉及交互语句起点，不能假设只把输入绑定变量就能正确恢复。优先让任务screen通过返回意图提交草稿，再在明确的脚本检查点保存；如采用交互内保存，应结合retain_after_load等机制并实测。不能把一个Python长循环中的所有交互当作独立可恢复检查点。

草稿JSON在用户停止输入约1秒后作原子替换备份，窗口失焦/退出时也尝试保存；由有明确触发点的动作完成，不能在screen预测中写文件。异常关机只能承诺恢复最近已落盘草稿，不承诺保存最后一个尚未落盘的字符。

运行中可以退出，同时终止本次进程树，不能把“正在运行”保存成通过。读档后恢复稳定编辑画面；未完成的本地任务不跨重启续跑，显示“需要重新验证”。仅复用已完整落盘且任务版本与源码hash匹配的完成收据。若读旧档发现较新草稿，只恢复草稿不恢复通关标记，必须重新验证。

### 9.3 读档、回滚与重复结果

剧情区允许查看历史；在任务提交和完成边界阻止跨越式回滚，任务内滚轮用于代码/输出滚动，不回退提交动作。保留正常读档入口，但每次读档、返回标题或切换任务都创建新的运行期界面会话标识。

结果应用前核对：当前界面会话、任务ID、任务版本、源码hash、代码修订号与提交ID。即使代码后来改回相同内容，也不能把早先任务的迟到结果直接应用到当前待验证状态。

通过后把完成收据、完成标记和待播放成功节点合并为一致状态，再自动保存，再播放动画。完成记录按run_id＋task_id唯一计数；重复轮询不会重复通关。首版奖励仅为结算中的“旧塔修复记录”，不设置可反复累加的货币。

重新开始创建新的run_id；读档沿用原run_id；结算后的自由试验使用practice标记，不覆盖主线收据。开发跳关使用debug标记，不计入真实完成率。

### 9.4 JSON导出与结算

提供“导出体验记录”，包括版本、三关结果、提交次数、错误类别、提示最高层级、首次理解题答案和有效体验时长。源代码是否附带可给一个勾选项，默认用于教师技术试验时附带。

JSON导出是普通记录格式，不冒充Ren’Py原生存档。首版不做任意JSON导入恢复游戏，也不承诺不同引擎版本存档兼容。引擎、任务内容和存档schema都锁定版本；发现不兼容时保留旧文件并清楚提示。

结算以事实陈述，例如“完成3项任务；使用第2级提示；理解题首次选择B”。有效时长排除最小化、明确暂停与等待编译运行的时间；无法可靠区分的挂机时间要注明。不显示“循环掌握度95%”一类无依据分数。

## 11. 分阶段开发与时间估计

以下为一名开发者借助AI、采用占位资源时的工作日估算，不含大量原创美术制作及目标设备应用准入流程。阶段门槛优先于日期；某个关键门槛未过，不通过添加剧情掩盖它。

| 阶段 | 估计 | 交付 | 进入下一阶段的条件 |
|---|---:|---|---|
| 1 单机技术实验台 | 3—5天 | 随包工具链、本地真实C执行、Ren’Py输入、6个方块灯 | 断网可用；正确/错误/死循环有真实反馈；进程可回收 |
| 2 三关完整流程 | 2—3天 | 三任务、三级提示、多用例、源码版本绑定 | 当前代码四用例统一验证，不混用结果 |
| 3 剧情与保存 | 2—3天 | 两场景、璃、分支、自动/手动存档、草稿 | 退出重进可继续，重复结果不重复推进 |
| 4 演出与打包 | 2—4天 | 灯光、门、世界展开、音效、离线Windows包 | 干净电脑首次离线启动；路径与权限测试通过 |
| 5 试玩与修订 | 1—2天 | 教师试玩、3—5名学生观察记录 | 修复主要卡点，列出尚未解决项 |

合计约10—17个开发工作日作为排期起点，不是工期承诺。美术完成度、随包工具链兼容、进程管理和输入控件体验可能影响工期。

### 阶段1最先做什么

只制作一个灰底术式界面：左边六个方块灯，右边代码片段、完整源码预览和输出。先验证正确循环、错误条件、故意缺分号、死循环、0输入、本地组件缺失、运行中退出，以及断网首次启动。不要先做完整片头或十几页设定。

阶段1有一个明确的引擎决策点：如果任务3的短代码输入仍严重影响操作，先判断是控件缺陷、键位冲突还是完整IDE需求。前两者修复后继续Ren’Py；若需求已变为长代码、多文件、频繁编辑，则重新评估独立网页代码工作台，并保留已做的本地判题模块；任何引擎调整仍须满足单机离线要求。不要默认“Monaco能直接塞进Ren’Py”。

## 12. 验收清单

| 编号 | 操作 | 必须观察到的结果 |
|---|---|---|
| A01 | 第一关运行0，再改1运行 | 0不通过；1通过并点亮1号 |
| A02 | 第二关先运行i<n，输入3 | stdout仅1、2；明确缺少3号 |
| A03 | 第二关改成i<=n | 得到1、2、3并通过当前输入 |
| A04 | 第三关对0、1、3、6统一验证 | 四组同一源码快照通过；0为空输出 |
| A05 | 循环块硬编码输出1、2、3 | n=3通过，其余相关用例失败；不能通关 |
| A06 | 输出重复、乱序、额外文本或空行 | 明确失败，不能靠灯全亮蒙混通过 |
| A07 | 删除分号/写错表达式 | 显示真实编译错误；不推进故事 |
| A08 | 写无限循环或无限输出 | 执行受限结束，界面可恢复，本地运行器可处理下一次且无残留进程 |
| A09 | 验证后修改代码，或取消等待后再编辑 | 通过标记失效；旧结果不能覆盖当前版本 |
| A10 | 连点提交、重复查询同一结果 | 不重复建同一请求，不重复完成任务 |
| A11 | 编辑一半保存、退出、重进 | 恢复已保存片段和对应任务；不回到最初模板 |
| A12 | 运行中退出或读旧档 | 保留草稿；未知结果要求查询/重验；不自动通过 |
| A13 | 读旧档并收到之前请求结果 | 会话检查阻止错误推进 |
| A14 | 开门动画完整看/直接跳过 | 都抵达同一残响和结算，完成记录只计一次 |
| A15 | 输入或粘贴{}[]%\、引号和换行 | 按原样提交显示；不触发标签解析或剧情快捷键 |
| A16 | 最低分辨率、静音、放大字体 | 关键按钮可见，反馈可读，任务可以完成 |
| A17 | 断开全部网络后首次启动并完成三关 | 编译、判题、演出、保存和重进全部可用，无下载请求 |
| A18 | 无开发环境的Windows x64电脑，以普通用户启动 | 使用随包组件真实运行；无需安装环境、改PATH或管理员权限 |
| A19 | 调试跳关与结算后重试 | 标记debug/practice，不污染主线学习记录 |
| A20 | 检查Wasm来宾能力和编译输入边界 | 无预开放目录/网络/宿主环境；不允许片段加入外部预处理指令 |
| A21 | 组件缺失、工具被阻止或工具异常退出 | 显示本地故障，保留草稿，不伪造通过、不要求关闭防护 |
| A22 | 中文/空格路径、只读游戏目录、移动游戏文件夹 | 编译仍可用；用户数据写入正确目录，原进度可找到 |
| A23 | 取消执行、强制结束游戏、再次启动 | 编译/运行进程树被回收，未完成提交需重新验证 |
| A24 | 关闭重开、磁盘写入失败 | 已提交进度正确恢复；写入失败明确提示，不虚报保存成功 |

测试数据和实际结果应随项目交付，未能实测的项明确写“未验证”。先人工完成关键端到端路径；自动化测试聚焦输出比较、源码版本绑定、结果去重等容易回归的逻辑。

性能目标暂设：正常短程序单次运行多数在3秒内返回、四组验证多数在8秒内完成；若超过目标先测清楚本机编译、运行器启动和结果回传分别耗时。性能目标在最低配置目标电脑上测冷启动和连续运行，并观察主界面响应。各学生电脑独立运行，不存在教师服务器并发容量要求。

## 13. 教师试玩安排

先由老师完整体验一遍，确认情节顺畅、输出解释没有概念错误、语法骨架不会造成误解；再请3—5名学生独立试玩，老师观察而不全程口头提示。

观察五件事：学生在第一关是否知道自己改了什么；第二关是否先查看输出；第三关是否理解“换输入而不换代码”；是否能解释0输入；是否想知道塔外发生什么。

记录卡包含：开始/结束、每关卡住的位置、最高提示级别、首次理解题答案、一句体验评价、是否愿意继续。若大量学生卡在操作，先修界面；若会操作但无法解释，补教学支架；若不愿继续，检查角色与任务动机。不能把所有问题都归为学生基础差。

## 14. 给开发AI的交接要求

请以本文件为需求规格，开发《旧塔的最后一盏灯》Ren’Py技术验证Demo。采用Ren’Py单机桌面游戏＋随包WASI SDK/Wasmtime＋本地真实C判题模块，按第11节逐阶段实现并提供可运行结果。

首次开发只完成阶段1：随包编译器与运行器、自定义输入screen、完整源码预览、本机真实编译运行、六个方块灯和错误反馈。第一项端到端验收必须在断网状态完成。先检查现有环境与仓库约束，记录使用版本；使用占位素材。

任务片段必须进入真实C模板编译执行；不得用源码字符串相等代替判题，不得使用固定成功动画伪装执行。判题使用完整输出、正常退出状态与同一源码快照；显示层只回放结果。

优先核验输入控件默认字符限制、Ren’Py文本转义、快捷键冲突、本地进程生命周期与存档检查点。编译执行不得发生于screen预测/渲染阶段；不能把进程句柄、管道和线程写进存档。所有任务通过、重复提交与迟到结果按照版本和会话检查。

每阶段报告：实现了什么、入口和启动方式、实际执行了哪些验收、哪些未验证、下一阶段依赖。遇到真实执行器不可用时报告阻塞，不得静默换成假判题。开发阶段可用带明确标识的测试桩验证界面，但最终验收必须使用随包工具在断网电脑上真实编译执行。

完成全Demo时交付第10节列出的源码、完整离线Windows包、本地工具清单、使用说明与测试记录。后续章节应复用任务控制器、判题适配器、灯光可视化接口、提示系统和保存逻辑。
