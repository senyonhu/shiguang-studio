# 拾光 Studio 实施交接与审查证据约定

这是实施 AI 的交付规范，也是后续审查者的检查入口说明。文件中的字段和示例是模板，不代表任何功能已完成。配合 [实施主提示词](implementation-agent-prompt.md) 与 [正式方案 v2](editor-player-ai-plan.md) 使用。

## 1. 目的与边界

让审查者先知道“做了什么、在哪里、怎样验证、还缺什么”，再沿关键调用链抽查和复跑。目标是减少无方向的全仓阅读，不是免除代码审查。

材料由实施 AI 生成，只是可验证的声明。指纹能绑定版本，不能证明逻辑正确或证据独立。关键链路必须由审查者重新运行；出现缺失、过期、不一致或高风险改动时扩大审查范围。

不要求每个函数都写说明，不复制所有源码到报告，也不靠巨量日志营造完整感。优先提供稳定符号、可复现命令、短调用链和真实错误输出。

## 2. 审查入口 HANDOFF.md

控制在约两页可阅读内容，使用链接指向详细证据。必须包含：

| 内容 | 要求 |
| --- | --- |
| 身份与范围 | 项目实际根目录、方案版本/散列、当前阶段、交付时间 |
| 本次结果 | 已实现且已验证、已实现未验证、模拟验证、未完成分别列明 |
| 代码版本 | Git 基线与 HEAD/未提交状态，或无 Git 的源码清单指纹 |
| 启动和复跑 | 已执行过的工作目录、命令、前置条件、预计耗时、测试数据位置 |
| 优先检查 | 最多 5 个风险点，附入口符号、测试及失败现象 |
| 主链路 | 人工/API/MCP → 服务 → 存储；生成任务 → 素材 → 绑定；预览 → 展示器 |
| 状态 | 已启动进程的用途/端口/停止方式、后台任务是否仍运行 |
| 后续工作 | 最早未完成需求、下一批范围、真实阻塞条件 |

不要在入口中输出令牌、请求认证头、用户隐私信息或大段原始源码。

## 3. 需求映射 requirements.json

为正式方案中的能力和验收要求建立稳定 ID。先覆盖完整方案，再按阶段细化；不要只列已经做完的功能。新增或改变 ID 必须保留旧记录的关联。

初始分组建议：

- `ARCH-*`：唯一后台、无界面运行、前端和插件边界。
- `EDIT-*`：人工编辑、对象模型、版本、事务、恢复、撤销、同步。
- `API-*`：查询、修改、认证、作用域、幂等、暂停、错误。
- `PLUGIN-*`：工具发现、协议调用、Skill 和宿主集成。
- `MEDIA-*`：图片/视频接口、任务、费用、下载、候选与绑定。
- `RUNTIME-*`：剧情、媒体、关卡、预览、存档和一致性。
- `RELEASE-*`：迁移、打包、离线运行、规模和文档。

每条记录至少有以下字段：

```json
{
  "id": "ARCH-001",
  "planRef": "docs/editor-player-ai-plan.md#5.1",
  "requirement": "外部 AI 仅通过插件/API 制作正式工程",
  "stage": "P0",
  "implementationStatus": "not_started",
  "verificationStatus": "not_run",
  "implementation": [],
  "tests": [],
  "evidence": [],
  "limitations": [],
  "lastReviewedSourceDigest": null
}
```

`planRef` 的章节号用于定位内容，不保证是可点击网页锚点；可另外增加实际 Markdown 锚点。

实现状态限定为 `not_started / in_progress / implemented / blocked`。验证状态限定为 `not_run / passed / failed / skipped / stale`。测试记录另带 `mode`，如 `unit / integration / fixture_provider / live_provider / manual`，防止“模拟通过”被误读为真实服务已接入。

`implementation` 条目包含文件路径、符号名和该位置的责任；`tests` 包含真实测试文件/用例名或人工步骤编号；`evidence` 指向 runId 与具体产物。`passed` 只对实际断言覆盖的能力有效。

例如测试适配器可证明任务重试和恢复，不可证明某商业服务的调用、画质或扣费行为。插件清单校验不可证明目标宿主已成功加载插件。

## 4. 模块与写入边界 architecture-map.md

至少包含：

1. 模块职责和依赖方向，注明持久化写入只能发生的位置。
2. 一条真实编辑调用链，列出路由、领域入口、提交与恢复函数。
3. 工具调用到后台的链路及协议版本。
4. 生成任务提交、查询、下载、登记素材和绑定事件的链路。
5. 预览与展示器共享哪些源码入口，哪些是环境适配。
6. 工程文件、数据库、日志、缓存、凭据、玩家存档分别放在哪里。
7. 重要设计选择、偏离正式方案的地方及理由；未确定事项明确写未确定。

源码位置使用“相对路径 + 导出的类/函数/路由名”；可附生成时行号，不以行号作为唯一定位。

列出所有读写正式工程、启动外部进程和调用生成服务的入口。存在多处文件系统调用并不自动违规，但必须能说明其用途和最终写入管理者。

## 5. 工具/API 映射 api-tool-map.json

优先从实际工具注册、路由和参数规范生成或校验，避免手写三份相互漂移的接口说明。每条包含：

- 工具名、API 方法/路径、适用协议版本。
- 输入/输出 Schema 所在位置。
- 路由处理函数、领域服务、持久化入口。
- 所需作用域，是否修改工程，是否可能调用付费服务。
- 幂等、版本冲突和异步任务语义。
- 对应集成测试及最近有效证据。

没有 API 对应的 UI 核心制作能力、没有实现的工具声明、同名但参数不一致的入口都列为缺口，不能在报告中隐去。

## 6. 基线与改动 changes.json

开发前先检查是否为 Git 仓库，不假定一定存在 `.git`。不要为便于交接擅自初始化、重置仓库或提交用户原有改动。

如果有 Git：记录基线提交、开始时的工作区差异和未跟踪文件；交付时记录本次差异，同时区分用户原有修改。仅有提交 SHA 不足以描述未提交工作区。

如果没有 Git：建立第一方源文件、配置、测试、正式设计及素材清单的路径/大小/SHA-256 基线，声明扫描范围和排除项。在首次修改已有文本文件前保存对应原始版本，以便生成可比较差异；新增、删除文件明确标记。

排除依赖目录、SDK、编译输出、缓存、大体积运行时和本轮证据目录，不盲目遍历 `node_modules` 或工具链。对实际修改的二进制素材保留来源、原始与新版本散列及可恢复位置。发现需要修改基线范围外文件时，先把它加入记录。

`changes.json` 每条至少包括：路径、增/改/删、对应需求 ID、修改原因、关键符号、之前/之后散列、关联测试。应由实际差异清单生成基础字段，再补充原因，不凭记忆列文件。

## 7. 每次验证的证据包

路径：`artifacts/studio-review/<run-id>/`，runId 唯一，不覆盖旧失败记录。仅保留足以复现与判断的内容；较大媒体记录路径与散列，并说明取得方式。最终交接要说明哪些证据仅存在本机，跨机器交接时不能留下断开的引用。

`run.json` 至少包含：

| 字段 | 内容 |
| --- | --- |
| runId、开始/结束时间 | 实际执行信息 |
| sourceDigest、digestManifest | 对本轮源文件、配置、测试和锁文件计算的确定性指纹与清单 |
| planDigest | 本轮依据的正式方案散列 |
| environment | 系统、运行时版本、与检查有关的依赖/媒体环境；不含秘密 |
| workingDirectory、commands | 实际目录和完整可复跑命令；敏感参数用凭据引用代替 |
| results | 用例名、需求 ID、模式、退出码、通过/失败/跳过/未执行、耗时 |
| evidence | 日志、请求轨迹、截图、预览、样板工程的相对路径 |
| limitations | 缺少凭据、服务不可用、环境限制或未覆盖行为 |

源码指纹排除证据包本身，避免循环散列。测试代码也必须进入指纹，不能修改断言后继续引用旧的通过结果。

生成 `artifacts.sha256` 校验本轮产物，清单自身不纳入自身散列。认证信息在产生证据时就应脱敏。请求轨迹至少保留请求 ID、工具/端点、非敏感必要输入、响应状态、对象 ID、修订和错误，不记录认证头或密钥。

修改相关代码、Schema、测试或配置后，旧证据可作为历史保留，但相应需求应标记 `stale`，直到重跑适当检查。若只改了不影响该链路的内容，可记录影响分析保留局部验证结论；最终完整交付仍需要一轮当前版本的核心集成检查。

## 8. 可复跑验证入口

实现至少一个有文档说明的本地验证入口。命令名称可按仓库习惯确定，先实现再在交接中写实际名称，不将计划中的命令冒充已存在。

建议分组：

- 快速组：协议、类型、关键单元行为及小工程集成检查。
- 核心组：真实后台进程、真实工具调用、持久化、重启、冲突、幂等、权限和恢复。
- 媒体组：测试适配器的图片/视频任务及真实文件加载；真实服务单独开关并受授权限制。
- 发布组：打包、独立运行、离线素材及敏感内容排除。
- 性能组：可配置规模的数据生成、实际测量和硬件记录。

测试应使用独立临时工程和测试凭据，不依赖用户作品。清理仅限本轮创建的测试目录/进程；不得结束用户其他任务或删除未知文件。

必要失败场景使用故障注入或可控测试适配器，但端到端声称必须有真实的服务边界调用。用 HTTP mock 不能证明后台进程运行；直接调用内部函数不能证明 MCP 工具已接通。

测试 UI 可以检查人工功能；不得将其作为 AI 制作入口。后台预览 API 输出的截图是渲染证据，不是桌面自动化行为。

## 9. 已知问题与分阶段状态

`known-issues.md` 每条记录：ID、影响、严重程度、复现步骤、预期/实际、关联需求、入口符号、建议修复位置及当前状态。

区分：实现缺陷、尚未实现、仅模拟验证、环境无法验证、正式方案变更。不使用“后续优化”笼统掩盖保存丢失、鉴权缺失、协议不通等核心问题。

按 P0—P5 记录阶段状态，阶段状态不能掩盖细分需求缺口。模拟媒体测试通过，可以满足接口预留要求；真实服务集成仍独立未完成。

## 10. 审查者的建议入口顺序

1. 阅读 HANDOFF.md，确认方案版本、改动范围和当前阶段。
2. 检查实际差异与 changes.json 是否一致、源码与证据指纹是否匹配、是否隐去未完成需求。
3. 复跑核心验证入口，抽查至少一个正常路径和相关失败路径；直接查看原始失败信息。
4. 沿写入链检查认证、版本、幂等、事务持久化和恢复；沿生成链检查任务重复、费用边界、下载与绑定冲突。
5. 检查工具/API/服务映射以及前端是否存在绕过后台的持久化；验证预览与展示器确实共用内核。
6. 独立读取本次高风险改动，不以实施 AI 自评替代判断。发现材料不可信、链路分叉或系统性问题时扩大阅读和测试范围。
7. 修复后生成新的证据包、更新受影响映射和问题状态；保留旧记录，清楚区分实施验证和后续审查验证。

## 11. 交付检查

- 所有引用的源码、符号、测试和证据确实存在。
- 每条已验证需求有当前版本证据；缺证据就降为未验证。
- 工具清单与实际可调用工具一致，后台启动和停止方式已验证。
- 模拟与真实结果分别列明；失败、跳过和未执行没有混入通过统计。
- 没有将凭据、未脱敏日志或用户作品内容写入交接材料。
- 续做位置明确，审查者能够从一份入口文档开始定位和复现。
