# Ren’Py 材料组装

用户提供材料和幕、帧、选项归属；AI 读取并理解资料，决定布局，通过插件操作工程。每帧是一轮推进前的完整状态，用户无需编程或准备程序格式。

先调用 `get_environment`，再用 `inspect_project` 选择或检查作品。使用当前工具清单中的真实工具和 schema；下文的运行工具尚未在当前宿主出现时，明确报告未连接，不用旁路脚本冒充 MCP 调用。

## 核心约定

- 保存的工程模型是内容依据，生成的 Ren’Py 文件是产物。修改通过项目对象，保留稳定的幕、帧、角色、组件、素材和选项 ID；展示顺序与身份分开。
- 完整帧没有前帧继承。未提供的背景、人物、附加组件和声音按空状态处理；不要替用户补造缺失内容。画面执行器可以保留相同显示对象，这不改变模型语义。
- 原文、选项结果和素材归属来自资料。AI 决定位置、尺寸、层级与统一风格，保存到 layout。对能从资料确定的关系自行处理；只询问无法判定的具体对应关系。
- 每次内容修改使用刚读取的 `expected_revision` 和独立 `operation_id`。相同意图、相同参数重试复用操作 ID；参数或目标版本改变时使用新的 ID。采用工具返回的新 revision。
- 用户说“只把人物移右一些”时，这是局部修改请求，不能重建整帧并清空其他内容。PATCH 省略与完整帧省略的含义不同。

## 制作与修改

首次组装时先读 [对象与参数实例](references/objects.md)，用实际 JSON 结构理解素材、完整帧、Flow 和局部布局，再读 [材料与排版](references/materials-and-layout.md)。先提取出处、登记素材，形成完整帧和流程；跨批前向引用通过候选导入一次提交。资料可按幕逐步提供，不要求完整作品一次到齐。

用户修改画面、重新导入原资料或恢复旧版本时，读 [修改与连续工作](references/changes.md)。先读取目标对象和 revision，保留已有布局和其他组件；重导入使用三方比较处理资料与聊天修改之间的差异。

作品需要插入 HTML 小游戏时，读 [HTML 小游戏制作与连续工作](references/html-minigames.md)。先发现当前能力及实际工具结构，再明确迁移 1.1；小游戏、类型变量与前向剧情引用通过候选一次提交，胜利、失败、取消和异常都有明确去向。玩法实测、玩家存档与独立发行各自需要对应证据。

## 运行与证据

内容提交后，用 `check_project`、`render_preview`、`test_routes` 和 `build_release` 执行相应任务；用 `get_job` 获取完成状态、日志和报告，用 `cancel_job` 取消受管任务。运行细节及结论边界见 [验证与交付](references/validation.md)。

实际打开截图检查中文、裁切、遮挡和层级；截图文件存在不等于视觉通过。结合用户预期检查各选项的去向和汇合。修复后检查新 revision；旧报告不能证明新内容可用。

分别说明材料解析、编译、布局、连续路线、声音、玩家交互和独立发行的已验证结果。未执行或报告未覆盖的门槛保留为未验证；`runnable_revision` 由真实路线测试设置，编译或单帧预览不能代替。

若当前任务要求 Codex 生成 demo 材料，使用可用的文字、图像和语音生成能力，再按同一导入流程组装。生成素材是外部能力，不在本插件中另建素材生成服务。图片生成与编辑使用对应可用工具，不用未说明的 Python 媒体修改替代。

交付时给出可编辑工程、有效预览/报告和任务要求的发行包，并注明版本、剩余问题及对应证据。完成后更新项目工作记录，使下次会话能从当前 revision 继续。
